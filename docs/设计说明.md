# 农子财务系统 · 设计说明

本文记录实现过程中的关键技术决策，以及需求书中**未明确、由实现方补充定义**的部分。
后者尤其需要业务方确认。

---

## 一、技术选型

### 为什么是 Node.js 而不是 Python

本机实测：Python 3.14.4 存在，但**没有 pip、没有 ensurepip，且 `bootstrap.pypa.io` 不可达**，
无法安装 Flask / SQLAlchemy / FastAPI 等任何第三方包。因此 Python 方案在本环境不可行。

Node.js 24 则可满足全部需求且**默认零依赖**：

| 需求 | 所用能力 |
| --- | --- |
| 内嵌数据库、开箱即用（8.1） | 内置 `node:sqlite` |
| 测试驱动开发 | 内置 `node:test` |
| 本地 HTTP 服务 | 内置 `node:http` |
| 密码加密 | 内置 `node:crypto`（scrypt） |

MySQL / PostgreSQL / SQL Server 的驱动作为**可选依赖**，只有真正切换到该数据库时才加载，
未安装时给出中文提示而非模块解析堆栈。

## 二、关键设计决策

### 1. 金额一律以「分」为单位的整数存储

财务系统最怕浮点误差。全链路整数运算，仅在前端展示时转成「元」。
这同时让建表语句在四种数据库间完全可移植——不需要依赖各库 `DECIMAL` 的行为差异。

已在测试中断言 `0.10 元 × 3 = 30 分`，杜绝 `0.1 × 3 = 0.30000000000000004` 一类问题。

### 2. 数据库适配层：统一异步接口

实测 `node:sqlite` 的 API 是**全同步**的，而 mysql2/pg/mssql 是异步的。
接口若做成同步，后三者无法实现，因此统一为 Promise 风格，SQLite 驱动把同步调用包成 Promise。

业务代码只依赖 `src/db/database.js` 暴露的 `query / one / run / insert / update / tx`，
从不 import 任何驱动，从而实现需求书 8.2「切换数据库后无需修改业务代码」。

### 3. ★ SQLite 的并发必须串行化

这是本项目最容易埋雷的地方，单独说明：

`node:sqlite` 只有一个同步句柄，而本层接口是异步的。在一次 `await` 让出事件循环的间隙，
另一个请求的语句可能被送进**同一个正处于未提交事务中的连接**。后果有两个：

- 两个并发事务互相看到对方未提交的数据（隔离性被破坏）
- 两个事务读到同一初值再各自回写，后写的覆盖先写的（**丢失更新**）

对财务系统而言，丢失更新意味着库存扣少、账目对不上。PostgreSQL / MySQL 不存在此问题，
因为它们的事务独占一条连接池连接；SQLite 只有一个句柄，只能靠互斥锁串行化。

`src/db/mutex.js` 实现了这把锁，并且**事务进行中的读也必须排队**（否则外部读会看到未提交数据）。
`tests/db/database.test.js` 中有一条并发自增测试专门守这条不变量：去掉锁即失败。

另有一条防呆：事务内误用 `db.query()`（而非事务句柄 `t.query()`）会立刻抛出明确的中文错误，
而不是永久等待自己持有的锁——后者表现为接口卡死且无任何报错，极难排查。

### 4. 出入库建模为「带方向的流水」

需求书 3.3 把字段列成「入库时间 / 入库量 / 出库时间 / 出库量」，那是**表单的形状，不是数据的形状**。
本实现建模为一行一次出入库（`direction` + `quantity` + `occurred_at`），于是：

- 3.4 的四种查询全部退化成一次 `GROUP BY`
- 天然支持按时间段筛选
- 实时库存 = 入库合计 − 出库合计，由流水推导，**不维护冗余列**，因此不存在对不上的可能

### 5. 销售与库存、财务的联动在同一事务内完成

销售单确认时，单头、明细、出库流水、收入流水在**同一次事务**内写入。
测试专门验证了「明细非法时整单回滚」——不留下半张单、半条出库流水，库存也不变动。

### 6. DATE 列必须用日期粒度的区间边界

`order_date` / `feedback_date` / `pay_date` 等 DATE 列存的是 `'2026-03-10'`，
而通用的时间段边界是 `'2026-03-10 00:00:00'`。字符串比较下前者小于后者，
于是 `order_date >= '2026-03-10 00:00:00'` **恒为假，区间查询会静默地一条都查不到**。

因此 `src/domain/daterange.js` 提供两套函数：`normalizeRange`（DATETIME 列）
与 `normalizeDateRange`（DATE 列）。所有 DATE 列的时间段测试都显式覆盖了「起止同日」这种情形。

以下每一项都是需求书里没有写、但实现必须有明确答案的地方。**请业务方逐条确认。**

| 1 | 「L2 经理层：管辖管理查询」 | 需求书未定义「管辖范围」的数据来源。补充为三个维度：**分管区域**（区域树，含下级）、**分管品种线**、**直属与全部下属**（按 `manager_id` 递归）。维护入口在「员工信息」中的分管区域设置。 |

| 8 | 销售确认后是否自动记账，需求书未说 | 默认自动生成「销售收入」流水，可在 `app_setting` 中关闭。本版在确认时确认收入，不建模应收账款与分期收款。 |
| 9 | 照片只写了字段，未说存储方式 | 暂存路径字符串，文件上传未实现（见 README 已知取舍）。 |
| 10 | 身份证与家庭住址未提访问限制 | 新增脱敏规则：**仅 L1 可见完整值**，其他职级看到 `110101********1234` 与 `***`。 |
| 11 | 数量单位未定义 | 数量为整数，单位文本默认「袋」。 |
| 12 | 未提审计要求 | 各表带 `created_at` / `updated_at` / `created_by`，另有 `audit_log` 表。财务系统没有留痕不可接受。 |
| 13 | 权限是否也约束写入，未说 | 读按数据范围过滤，写按权限码控制。L2 不得在分管区域外新建经销商。 |
| 14 | 「所有员工发放工资支出」是否受权限限制 | 受。与 2.2「权限应贯穿所有模块的统计汇总」一致，L2 看到的「所有员工」是其管辖范围内的员工。 |
| 15 | 时间段是否含端点 | 统一采用**左闭右开** `[起, 止+1天)`，起止同日即只覆盖当天。避免 `23:59:59.999` 一类差一错误。 |
| 16 | 时区未说明 | 一律按**本地时间**存储为 `'YYYY-MM-DD HH:MM:SS'` 字符串，不使用 `toISOString()`（会按 UTC 输出，导致中国时区日期整体偏移）。PostgreSQL 使用不带时区的 `TIMESTAMP`。 |

## 四、权限模型

```
L1 高管层 → 全部数据
L2 经理层 → 分管区域（含下级区域） ∪ 分管品种线 ∪ 本人及全部下属
L3 员工层 → 仅本人经手的记录
```

由 `src/domain/scope.js` 的 `buildScope` 算出范围，`applyScope` 翻译成 SQL 条件，
所有模块的读接口都经过它。这条机制是需求书 2.2「权限应贯穿所有模块」的落地方式。

**失败时收紧，绝不放开**：若某 L2 既没有分管区域、也没有下属，其范围为空，
看到的是空系统而不是整个公司的数据——漏配管辖范围不应导致数据泄漏。

**数据范围只从服务端会话计算**，前端传什么参数都无法放宽。
端到端测试中专门有一条：L3 手工拼接 `?regionId=` 也拿不到辖区外数据。

## 五、测试策略

共 390 条测试，约 2 秒跑完。分层如下：

| 层次 | 位置 | 验证内容 |
| --- | --- | --- |
| 纯逻辑 | `tests/domain/` | 金额、时间段、权限范围、SQL 扫描（引号/注释感知的占位符重写） |
| 数据库 | `tests/db/` | 建表、迁移幂等、校验和、事务回滚与嵌套、并发串行化 |
| 业务模块 | `tests/service/` | 各模块 CRUD 与需求书中的每一条查询 |
| 端到端 | `tests/http/` | 真实起服务、真实发请求，含三级权限隔离与跨模块联动 |

其中 SQL 扫描器（`src/db/sql/scan.js`）拿了最密的测试：把 `?` 占位符错误地改写进
`LIKE '%?%'` 或中文注释里，是整个数据库抽象层最容易发生的静默错误。

## 六、目录职责

| 目录 | 职责 | 约束 |
| --- | --- | --- |
| `src/domain/` | 纯逻辑 | 不做任何 I/O，可 100% 单测 |
| `src/db/` | 数据库抽象 | 只有这里 import 驱动 |
| `src/services/` | 业务规则 | 以 `ctx`（含 `user` 与 `scope`）为第一个参数 |
| `src/http/` | 路由与响应 | 不做权限判断，交给服务层 |
| `src/web/` | 前端 | 零构建，权限过滤仅用于界面整洁，真正的判定在服务端 |
